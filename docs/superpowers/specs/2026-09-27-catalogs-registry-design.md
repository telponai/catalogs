# TelponAI Catalogs Registry — Design

Date: 2026-09-27
Status: Proposed for review

## Goal

Create `github.com/telponai/catalogs` as the public source-of-truth registry for web apps shown in the built-in TelponAI Catalogs experience.

Adding or changing an app must require only a pull request or commit to this repository. TelponAI itself must not need to be rebuilt or redeployed for each catalog change.

The first catalog entry is:

- Name: YouTube Music Player
- URL: `https://jacob7179.github.io/YouTube-Music-Player-Web/`
- Source: `https://github.com/Jacob7179/YouTube-Music-Player-Web`
- Category: `music`

## Product model

Catalogs and Apps are separate concepts:

- **Catalogs** is a public, remotely updated, read-only registry.
- **Apps** is the user's local library stored on their device.
- A catalog app can be opened directly without installing it.
- A catalog app can optionally be saved into Apps for local persistence.
- Opening a catalog app reuses TelponAI's existing HTTPS iframe mini-app viewer.
## Repository layout

```text
apps/
  youtube-music-player.yaml
schemas/
  app.schema.json
scripts/
  build-catalog.mjs
dist/
  catalog.json
.github/workflows/
  catalog.yml
README.md
CONTRIBUTING.md
```

Rules:

- `apps/*.yaml` is the only hand-edited app registry.
- One app equals one YAML file.
- The filename must equal `<id>.yaml`.
- `dist/catalog.json` is generated and must never be edited by hand.
- `schemas/app.schema.json` defines the machine-readable V1 contract.
- CI validates every source file before publishing a new manifest.

## YAML source contract

V1 required fields are `schemaVersion`, `id`, `name`, `description`, `url`, and `category`.
Optional V1 fields are `icon`, `source`, `tags`, and `author`.

Example:

```yaml
schemaVersion: 1
id: youtube-music-player
name: YouTube Music Player
description: A feature-rich web music player powered by YouTube.
url: https://jacob7179.github.io/YouTube-Music-Player-Web/
category: music
source: https://github.com/Jacob7179/YouTube-Music-Player-Web
tags:
  - music
  - youtube
  - player
author: Jacob7179
```

`icon` is intentionally omitted here. Omission means automatic favicon discovery; there is no magic `icon: auto` sentinel.

## Validation rules

- `schemaVersion` must equal integer `1`.
- `id` must match `^[a-z0-9]+(?:-[a-z0-9]+)*$` and be at most 80 characters.
- `name` must be non-empty and at most 160 characters.
- `description` must be non-empty and at most 500 characters.
- `url`, `source`, and absolute `icon` values must use HTTPS.
- `category` must be lowercase kebab-case.
- `tags`, when present, must contain unique lowercase kebab-case values.
- `author`, when present, must be a non-empty string at most 160 characters.
- The YAML filename must exactly match `<id>.yaml`.
- IDs must be unique across the repository.
- App URLs must be unique across the repository after URL normalization.
- Unknown top-level fields are rejected in V1 to catch typos early.

Unsafe URL schemes such as `javascript:`, `data:`, `file:`, and plain HTTP are rejected.

## Generated runtime manifest

CI compiles valid YAML into `dist/catalog.json`. TelponAI consumes JSON, not YAML, so the browser requires no YAML parser and runtime parsing stays deterministic.

Example shape:

```json
{
  "schemaVersion": 1,
  "generatedAt": "2026-09-27T00:00:00.000Z",
  "apps": [
    {
      "id": "youtube-music-player",
      "name": "YouTube Music Player",
      "description": "A feature-rich web music player powered by YouTube.",
      "url": "https://jacob7179.github.io/YouTube-Music-Player-Web/",
      "category": "music",
      "source": "https://github.com/Jacob7179/YouTube-Music-Player-Web"
    }
  ]
}
```
`generatedAt` is generated by CI and never authored manually.

Apps are sorted deterministically by `id` before output so builds are stable apart from `generatedAt`.

## Build and publishing pipeline

On pull requests:

1. Parse every `apps/*.yaml` file with a safe YAML parser.
2. Validate each entry against `schemas/app.schema.json`.
3. Run repository-level checks for filename, duplicate ID, and duplicate normalized URL.
4. Build `dist/catalog.json` in memory.
5. Fail if validation or generation fails.

On pushes to `main`:

1. Run the same validation and build.
2. Write the generated runtime manifest.
3. Publish the generated artifact through GitHub Pages.
4. The stable consumer URL is `https://telponai.github.io/catalogs/catalog.json`.

The client must not call the GitHub API for normal catalog loading. This avoids API authentication and rate-limit coupling.

## Icon resolution

Icon discovery is best-effort enrichment and must never block publication of an otherwise valid app.

Resolution order:

1. Use explicit `icon` from YAML when present.
2. During registry build, fetch the app HTML with a short timeout and resolve its declared `<link rel="icon">` URL.
3. If discovery is unavailable, use `/favicon.ico` on the app origin as the runtime candidate.
4. If that image fails to load, the TelponAI client shows its built-in generic web-app icon.

The generated manifest carries the resolved HTTPS `icon` URL when one is available. Favicon HTML discovery is intentionally done in CI rather than in the browser because cross-origin HTML inspection is not reliably available to the TelponAI client. Network failure during favicon discovery is non-fatal.

## TelponAI client integration

The existing TelponAI website already has an Apps screen, HTTPS URL validation, local app storage, and an iframe viewer. Catalogs must reuse those primitives rather than introduce a second launcher.

The Apps screen gains a `Browse Catalogs` entry that opens a Catalogs view with:

- search by app name, description, and tags;
- category filtering;
- cards showing icon, name, short description, and category;
- `Open` to launch immediately in the existing iframe viewer;
- `Add to Apps` to persist the same URL/name into the existing local app library.

Catalog entries themselves are never written into local storage unless the user explicitly adds one to Apps. The manifest cache is separate from the local app library.

## Fetching and offline behavior

The Catalogs client uses stale-while-revalidate behavior:

1. Render a previously cached valid manifest immediately when available.
2. Fetch the current manifest in the background.
3. Validate the top-level version and required app fields before replacing cache.
4. Replace the cache atomically only after the full manifest validates.
5. Keep the last known-good cache if fetch, JSON parsing, or validation fails.

A first-time offline user sees an explicit `Catalog unavailable offline` empty state instead of an error loop.

The remote manifest is public metadata only. User files, local apps, preferences, and catalog usage are not uploaded to the registry.
## Security and trust boundaries

Registry metadata is untrusted input even though it comes from the TelponAI organization.

Client requirements:

- Revalidate catalog URLs as HTTPS before launch or persistence.
- Never render description/name as HTML.
- Never execute script or markup from registry fields.
- Preserve the current iframe sandbox and permission allowlist.
- Do not grant additional iframe capabilities based on catalog metadata in V1.
- Treat external icons as untrusted images with normal browser isolation.
- Do not proxy arbitrary catalog app traffic through the TelponAI server.

Repository CI requirements:

- Reject YAML aliases or parser features that can create surprising object graphs.
- Reject duplicate keys.
- Reject unknown schema fields.
- Pin CI actions to stable major versions or commit SHAs.
- Use the minimum GitHub Actions permissions needed to validate and publish Pages.

## Failure handling

A single malformed YAML file fails CI and prevents publication of a partial new manifest.

A broken external app or icon does not invalidate the manifest. Catalogs can still list the entry and offer `Open site` in a new tab if its iframe cannot render due to the destination site's own framing policy.

If a catalog app later disappears, the registry entry can be removed in a normal commit. Locally saved Apps remain local shortcuts until the user removes them.
## Testing strategy

Registry repository tests:

- valid YAML builds expected JSON;
- required-field omission fails;
- malformed YAML fails;
- duplicate YAML keys fail;
- unknown fields fail;
- unsafe/non-HTTPS URLs fail;
- filename/id mismatch fails;
- duplicate ID fails;
- duplicate normalized URL fails;
- output ordering is deterministic;
- the initial YouTube Music Player entry is present in generated output.

TelponAI client tests:

- cached manifest renders before network refresh;
- valid refresh replaces cache;
- invalid refresh preserves last known-good cache;
- first-use offline state is explicit;
- search and category filtering work;
- `Open` uses the existing iframe viewer;
- `Add to Apps` calls the existing local app persistence path;
- invalid remote URL is refused by client-side HTTPS validation;
- icon failure falls back without breaking the card.

Browser E2E verifies that the initial YouTube Music Player entry appears in Catalogs and can be launched from the Catalogs UI.
## Acceptance criteria

V1 is complete when all of the following are true:

1. `telponai/catalogs` contains versioned YAML schema, validator/build tooling, documentation, CI, and the initial YouTube Music Player YAML entry.
2. A pull request with invalid catalog metadata fails before merge.
3. A push to `main` publishes a valid `catalog.json` without a TelponAI deployment.
4. TelponAI Catalogs loads the published manifest and shows the initial app.
5. The initial app uses an automatically resolved favicon when no explicit icon is provided.
6. The initial app can be opened in TelponAI's existing mini-app iframe viewer.
7. The initial app can be added to the user's local Apps library.
8. Catalogs continues to show its last valid manifest when the registry is temporarily unavailable.
9. No catalog operation uploads the user's local data to TelponAI or GitHub.

## Non-goals for V1

- Ratings, reviews, download counts, or analytics.
- Accounts or server-side user libraries.
- Executable packages or source-code mirroring.
- Arbitrary iframe permission declarations from catalog YAML.
- Automatic repository crawling to discover apps.
- A web-based catalog submission editor.
- Moderation queues beyond normal GitHub pull-request review.
- Treating the catalog as an app package manager.

The registry distributes metadata only; each app continues to run from its own HTTPS origin.
